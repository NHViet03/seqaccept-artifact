Summary

SeqAccept replaces "stop at the first green run" with a betting test per candidate over randomized test blocks, so a lucky pass on a flaky suite does not end the repair loop. We implemented it with its baselines, used four LLMs as repair agents on 17 planted bugs in 10 repositories from the IDoFT flaky-test dataset, and added injected flakiness with known rates.

1 The proposal

A repair agent writes a patch, runs the tests and stops when they pass. If some failures are random, the patch that ends the loop was picked because its run was green, and a green run then says little. If q is the chance that a broken patch passes one run, trying n broken candidates gives up to 1 − (1 − q)n chance of accepting one.

SeqAccept guarantees that the chance of ever accepting a patch whose failure probability exceeds ε is at most α, at any stopping time. It has three parts:

  1. Block e-processes. Each candidate gets its own betting e-process over blocks (random subsets of tests, random order, fresh container). This stays valid for order-dependent suites.
  2. Error spending with refunds. Candidate j is accepted when its e-value reaches 1/αj, a share of the remaining budget. Rejecting a candidate returns what it did not spend.
  3. Cost-aware allocation. It directs tests at the requirement that limits acceptance most. The pilot leaves it out (one requirement per bug).

The paper projects that false acceptance falls from 18.4% (stop-on-first-pass) and 9.1% (majority-of-5) to 2.3%, at about 16 times majority-of-5's budget. Its results section is still a projection, so this pilot is the first measurement. We used α = 0.05, ε = p0 + 0.05, spending share 1/2, a truncated Kelly bet, a cap of 800 blocks per candidate (D1) and refunds on rejection only (D3).

2.2 Data

Flaky tests come from IDoFT's Python list. We screened its 110 live repo/commit pairs in Docker. Tests had to run offline, the flake had to reproduce under random order, and the repo had to fail under 5% (p0) without the flaky tests. 22 pairs passed (28 failed the p0 check, 20 had tests that do not run, 14 did not reproduce, 13 failed to build, 10 needed missing modules, 3 had no tests left). Ten of the 22 have planted bugs and are used here.

An agent planted a bug of at most two changed lines in one file per repo, so the correct patch is the original line. A separate agent wrote each bug report from the failing test output alone, without the original file or the diff, so the report cannot leak the fix. Seven bugs are ordinary logic errors and three are order bugs (state leaking between tests). Each repository then got a second bug, planted and reported the same way (D19). QTAF's second bug made the tests fail in only 4% of blocks, too few to tell it from p0, so it failed the bug check. Kanren's is left out (D23). Table 1b lists the eight we use.

Four models act as the repair agent. gpt-4.1-mini (baseline), gpt-4o (weaker) and grok-4.7 (stronger) run on one Azure endpoint. llama3.1:8b, a small open model, runs locally through Ollama with a 96k-token window (D22). The agent gets the report and the buggy file, replies with a full corrected file, and keeps going after a green run, because the stopping rule is applied later, offline. Each attempt gets one block of feedback, which is not reused as evidence. A stream holds up to 15 candidates (temperature 0.8). Replies with no code are skipped, so gpt-4o streams average 11.8 candidates. Each repo and model pair is recorded twice.

2.3 Ground truth and replay

We record once and replay offline, so every rule sees the same candidates. Each distinct candidate runs 400 blocks in fresh containers: 200 set its true failure probability p (the truth set) and 200 form the pool the rules draw from. A candidate that fails at least 75% of its first 40 blocks stops there. A candidate is Correct if p < p0 + 0.01, Broken if p > p0 + 0.05, and marginal otherwise. Each rule is replayed 20 times per episode and scored against the truth label. An episode's replay seed comes from its file name, so adding or dropping other episodes leaves its draws unchanged.

2.4 Making the tests flaky

Ordinary bugs fail every time, so a broken patch never gets lucky and cannot test the method. We use two sources of flakiness.

  • Natural: order bugs and OD repos fail depending on test order under randomized blocks. Nothing is injected.
  • Injected: a pytest plugin (flakeinject.py) flips test results after each call, seeded by the block seed so blocks are reproducible. Only the test call flips, so a patch that breaks an import still fails every time. Bernoulli mode flips each test independently. Markov mode uses a hidden flaky state that tests walk through in run order, which gives bursts.

2.5 Tools and deviations

  • Docker Desktop on an Apple-silicon Mac (18 cores, 27 GB for Docker), 8 to 12 offline containers at a time. The run executed about 977,000 blocks, roughly 817 container-hours (summed block time).
  • run_all.py runs every step from one command and resumes from a ledger and per-candidate block checkpoints. A lock blocks a second run, and a Docker outage stops the run instead of recording fake failures.
  • 257 automated tests pass. A conformance guard fails if code is not traced to a paper section, a fixed constant changes, or seq_accept drifts from a line-by-line copy of Algorithm 1.

3.4 Near the boundary

SeqAccept accepted no broken patch, but that alone does not test its bound. The guarantee binds only for broken patches that fail just above ε. Only 23 of the 1841 broken candidates fail within 0.05 of ε. The rest fail far more often and are rejected quickly. We checked the boundary in two ways.

It accepts clean candidates, and accepts one at p = 0.05 in 0.95% of runs, at 0.06 in 0.10%, and at 0.07 or above never. A stream of 15 broken candidates all at p = 0.051 is the worst case. The price is blocks. In the p = 0.051 streams of 15 candidates a run costs 2,528 blocks for B4, 10,184 for B5 and 11,645 for SeqAccept. B4 is cheaper mostly because it stops early on a false accept, so budgets here are not matched and B4's saving is not a like-for-like one. On the real streams (Table 4) all of B4, B5, B6 and SeqAccept sit near 0%, because broken candidates there fail far above ε. Table 8b is therefore the test of the guarantee, and Table 9 shows the same ordering on real candidates once they are moved near ε.

Boundary stress on the real streams (D14). To put real candidates near ε, we replay the 136 natural episodes through a weaker oracle. Each recorded failed block is read as passed with a known probability m, drawn fresh on every replay draw. This models a bug the tests catch only rarely. Every failure rate, p0 included, scales by 1 − m, and labels use the scaled truth rate. A patch that always fails then fails 20%, 10% or 6% of blocks. No new blocks are run.

With m = 0.94, 452 broken candidates sit at about p = ε + 0.01. The baselines accept one in 26 to 27% of episodes, and SeqAccept in 0.19% (51 of 27,200 runs), at a high price: about 2513 blocks per accept. Across the three masks B4 accepts a broken one in 2.9 to 10.7% of episodes, up to twice α, because checking an interval after every block is not valid. B5 reaches 1.5% at m = 0.94, about 8 times SeqAccept, because every candidate gets the full α. Across the sweep SeqAccept's FAR is 0.05 to 0.19%, in line with the simulation's 0.1 to 0.3% at p = 0.05 to 0.06, and far below α. What grows is the marginal-accept rate (15%): SeqAccept ends on candidates that fail just under ε, which is what it promises. So the 0% in Table 4 comes from where real candidates sit, not from a broken implementation. The paper's 1 to 3% needs every broken candidate to sit within about 0.001 of ε, which real agent streams do not do.

3.6 SeqAccept in the loop

Each model ran the 21 first-bug tasks once (freezegun left out, D18) with the same budget of 15 replies. The accepted fix was then labelled on 200 fresh truth blocks.

3.9 Limitations

  • Freezegun's first bug and kanren's second bug are left out for every model (D18, D23, 3.1), because grok-4.7 could not record them. The other models' recordings are dropped so that all four score the same 82 episodes.
  • The online subset (3.6) has 21 episodes per model and one run, so it shows that the loop never ended on a broken fix but cannot estimate a small rate.
  • The refund result (3.5) comes from built streams, not from agents that failed 40 times in a row. Its candidates are real, but their order is not.
  • The injection-rate sweep (D17) covers the first bugs only, not the second bugs.
  • The boundary-stress runs (3.4) share candidates across their 200 replications, so the false-accept counts are not independent events.
  • Ten repos with one or two planted bugs each give wide intervals and partly confound repo with bug. Twelve screened repos are still unused.
  • Blocks recorded before the 180 s cap (some kanren candidates and the pdir2 stall) are charged at most 180 s in the budget, as the cap would have killed them (D9). Their pass or fail outcome is kept as recorded.
  • B7 (protected hidden tests) is implemented but was withdrawn before its streams were recorded (D21), so we cannot say whether the gain is statistical or comes from a better oracle. B8 (flaky-detector gating: quarantine known flaky tests, then B1) is identical to B1 here, because every task already drops those tests. Cost-aware allocation and epoch resets are left out by plan.

4 Conclusion: using SeqAccept across models

SeqAccept accepted no broken patch with any of the four models, offline or in the loop, so its safety did not depend on which model wrote the patches. What changed with the model was how much the baselines got wrong, how often the loop ended in an accept, and what the guarantee cost.

The baselines suffer most from broken patches that pass by luck, and the models differ in how many they write. llama3.1:8b writes the most broken candidates (74%), and 118 of its 374 natural ones pass at least one block in ten, so B1 accepts a broken patch in 45% of its episodes. gpt-4o writes 56% broken candidates, but 114 of its 211 natural ones pass fewer than 1% of blocks, so a lucky pass is rarer. gpt-4.1-mini writes fewer broken candidates (26%), yet 86 of its 122 are of the lucky kind, and the two end with similar B1 FAR (27.1% and 25.1%). grok-4.7 writes few broken candidates (10%), but 38 of its 42 are of the lucky kind, and B1 still accepts a broken patch in 9% of episodes. A stronger model lowers the baselines' error without removing it, because the broken patches it does write are the hard ones to catch. SeqAccept removes 45, 27, 25 and 9 points of false accepts for llama3.1:8b, gpt-4o, gpt-4.1-mini and grok-4.7.

The weaker the model, the more episodes hold no correct candidate at all: 54, 30, 19 and 1 of 82 for llama3.1:8b, gpt-4o, gpt-4.1-mini and grok-4.7. SeqAccept accepts nothing there, so it ends in an accept in 34, 66, 77 and 100% of runs, against 71, 89, 93 and 100% for B1. That is the correct outcome and explains part of the FAR gap, but it also means the agent's 15 attempts bought no accepted patch, and something else has to take over: a human, a stronger model or a longer search. The online subset shows the same pattern (3.6). llama3.1:8b ended without an accept in 14 of 21 episodes, grok-4.7 in none.

The price of a certified accept ranges from 181 blocks for grok-4.7 to 563 for llama3.1:8b, which has to reject many broken candidates before it reaches a correct one. Against B1 the guarantee costs most for grok-4.7 (119x) and least for gpt-4o (24x), because a strong model's first patch is often right and B1 then stops after about one block. In absolute test time per episode the order is gpt-4.1-mini (483 s), llama3.1:8b (372 s), gpt-4o (357 s) and grok-4.7 (268 s). SeqAccept therefore pays off most where a wrong accept is expensive and the model often writes broken patches that tests pass by luck. For a strong model on a low-stakes repository the guarantee still removes 9 points of false accepts, at about 119 times B1's test time.

On this data B4 (fixed-sample CI) was nearly as safe as SeqAccept for every model (4 false accepts in 6,560 runs) at about 43% of the blocks per accept. The case for SeqAccept over B4 therefore rests on the boundary stress (3.4), where B4 reaches about twice α, not on any per-model result. The late streams (3.5) separate SeqAccept from B6, not from B4. The model comparison is descriptive: four models, ten repositories with one or two planted bugs, a model effect that is mixed with repository and bug, and 82 episodes per model. We ran no significance test between models.
